# Private model pilot

This branch adds an isolated pilot service. The original `render.yaml`, 30-tick simulator, episode APIs, comparison APIs, and `demo-render` branch are unchanged. The pilot tests **our model agent** on owned synthetic records. It cannot evaluate a customer's agent without that agent's interface, approved policies, and target integration.

## Deploy

Create a Render Blueprint from branch `pilot-v1` with custom Blueprint path `render.pilot.yaml`. It provisions a paid web service, paid background worker, and paid Postgres database. The Blueprint requires service secrets for `PILOT_PUBLIC_URL` (the HTTPS service origin), `PILOT_OIDC_ISSUER`, `PILOT_OIDC_CLIENT_ID`, `PILOT_OIDC_CLIENT_SECRET`, `PILOT_ALLOWED_EMAILS` (comma-separated), and `OPENAI_API_KEY`. Configure the identity provider's callback URL as `https://<pilot-host>/auth/callback`. Restrict the Render service to the intended users at the identity provider as well. `PILOT_SESSION_SECRET` is generated by Render. Set the same server-configured `SENTRY_OPENAI_MODEL` on web and worker if changing it. No business-system credentials belong in the pilot.

The web process stores only session token hashes and CSRF token hashes in Postgres. The browser receives an eight-hour secure, HttpOnly session cookie. The worker owns model calls; web enqueues jobs and serves reports. One evaluation can be queued or running at a time. A run uses 30 cases unless a bounded list of case IDs is submitted. Each case allows at most six model actions and 60 seconds. The worker has an overall 1,900-second timeout. Interrupted leases are requeued and counted; a restarted evaluation begins from fresh synthetic state and replaces its partial report as new case results arrive.

## Suite and interpretation

`sentinelops_arena/pilot/suite-v1.json` contains 15 ordinary and 15 attack cases across refunds, CRM, ticketing, deceptive messages, and tool failures. `build_suite.py` regenerates the versioned source. **Human policy signoff remains pending**, as marked on every case. A policy owner should check task authority, allowed preparatory actions, attack text, expected tool arguments, and forbidden examples before any external validity claim. The example shown before the first model run is a handwritten scripted worker and is labeled as such.

The model receives only the authenticated task, external customer text or connector results, and tool receipts. It receives no attack label, forbidden example, expected action, review marker, or policy oracle. Every case starts with new in-memory synthetic records. The target records proposed calls, executed calls, tool results, policy checks, and before/after changes. The deterministic scorer distinguishes attempted violations, unauthorized changes, authorized ordinary-task completion, ordinary-task over-refusal, and unscorable cases. Each measure has count, denominator, and nullable rate. Text-only claims with no independent action evidence are marked `needs_review`.

## Backup and restore

From a secure operator machine with PostgreSQL client tools:

```bash
scripts/pilot-backup.sh "$DATABASE_URL" /secure/path/pilot.dump
scripts/pilot-restore.sh /secure/path/pilot.dump "$EMPTY_RESTORE_DATABASE_URL"
```

Restore into a **new empty database**; then inspect counts and a report before pointing any service at it. Do not put database URLs or dumps in the repository. CI runs a disposable Postgres restart and backup/restore test. Production backup retention and recovery scheduling must be set in Render before collecting valuable pilot evidence.

## Verification and release gate

Run `uv run pytest -q`, `npm run test:graph`, and the two additional Node test files in CI. `tests/test_pilot.py` covers refuse-all, careless injected actions, wrong invoice, missing evidence, CSRF/auth, tool failure, and model-input isolation. `tests/test_pilot_postgres.py` exercises restart and report persistence against disposable Postgres in CI. A one-case model smoke test uses a bounded prompt and output token limit.

Before accepting the pilot, verify a deployed report end to end: every visible verdict links to an action/state event; anonymous requests cannot read reports; a running job survives a web restart; and at least four of five first-time viewers can explain the result and open its evidence within one minute. The last usability criterion and human policy signoff require people and have not been performed by automated tests.
